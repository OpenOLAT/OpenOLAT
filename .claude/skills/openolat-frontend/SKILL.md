# OpenOlat Frontend & Theming Assistant

You are an expert in OpenOlat's frontend architecture: SASS theming, CSS class conventions, DOM structure, component rendering, and responsive design. Use the knowledge below and the reference files to help developers style components, create themes, debug layout issues, and understand the rendering pipeline.

For compressed frontend knowledge, read `.claude/openolat-frontend-knowledge.md`

For detailed frontend documentation, read: `doc/openolat-frontend.md`

For visual documentation with SVG diagrams, open: `doc/openolat-frontend.html`

For live rendered component examples with theme switching, open: `doc/component-library/index.html` (pages: buttons, forms, tables, navigation, feedback, layout, data display, AI UI, room management; all examples use real markup read from the renderers or the localhost DOM)

`doc/openolat-frontend.md` and `doc/openolat-frontend.html` have the same 37 chapters and numbering. Chapter 35 is the info page pattern, chapter 36 the accessibility chapter.

State of this skill: release 21.1.0 (2026-09-25). `**New in 21.1.0:**` marks changes of 21.1.0. For new components check the GUI demo site (navbar More > gui_demo, needs `guidemo.enabled=true`) and read the rendered DOM there.

## Technology Stack

- **Bootstrap 3.4.1** (SASS): grid, buttons, forms, navs, modals
- **Font Awesome 6.7.2**: icons (`o_icon o_icon_{name}`)
- **jQuery 3.7.1**: DOM manipulation, AJAX
- **Vanilla JS Datepicker 1.3.4**, **typeahead.js**, **D3.js 7.9.0** (charts), **TinyMCE 6.8.6**, **FullCalendar 6.1.15**, **Leaflet 1.9.4**
- **Apache Velocity**: server-side `.html` templates in `_content/` dirs
- **~540 Java ComponentRenderers**: programmatic HTML generation
- **~100 SASS modules**: OpenOlat-specific styling in `themes/light/modules/`
- **Dart Sass >= 1.79.0**: compilation via `compiletheme.sh`
- **No client-side framework**: all UI state lives on the server

## Theme Inheritance

```
Custom theme config (pre-import, no !default)
  → light/theme.scss
    → _functions.scss (a11y color utilities)
    → _config.scss (1500+ variables with !default; custom values win)
    → _modules.scss (100 module files including Bootstrap)
    → _patches.scss
  → Custom theme CSS overrides (post-import)
```

Three CSS outputs: `theme.css` (main app), `content.css` (iFrames), `email.css` (notifications). `light` also builds `oo-docs.css` (icons for the manual).

## Variable Naming

- `$o-` prefix = OpenOlat-specific (e.g., `$o-navbar-height`, `$o-tree-link-color`)
- No prefix = Bootstrap standard (e.g., `$brand-primary`, `$font-size-base`)

## Page DOM Skeleton

```html
<body id="o_body" class="[o_dmz]">
  #o_navbar_wrapper > #o_navbar_container > .o_navbar
    .o_navbar-brand | .o_navbar_tabs | ul#o_navbar_tools_permanent (#o_navbar_search_opener, #o_navbar_my_menu)
  #o_main_wrapper > #o_main_container
    TooledStackedPanel (.o_with_toolbar .o_with_breadcrumb)
      #o_main_toolbar .o_toolbar       ← breadcrumb + tools (SIBLING of #o_main)
      #o_main (CSS Grid: auto | 1fr | auto)
        #o_main_left (tree) | #o_main_center (content) | #o_main_right (sidebar)
  #o_footer_wrapper > #o_footer_container
```

**Important:** `#o_main_toolbar` is a **sibling** of `#o_main`, not a child. Both live inside the TooledStackedPanel. Some pages (catalog, coaching) have no `#o_main` at all.

Column visibility via: `.o_hide_main_left`, `.o_hide_main_right` on `#o_main`.

## Status Colours and Token Layers

Status colours: 8 semantic states in `$o-states` (`_palette.scss`): neutral blue, success green, warning yellow, critical orange, danger red, finished brown, inactive slate, highlight magenta. 5 styles: solid (default), dark (counters, deleted), tint (draft, preparation), light (not seen), text (outline, `o_labeled_light`). All foregrounds reach 4.5:1, checked at compile time.

- New status: `<span class="o_labeled o_state_success">`, modifiers `o_state_dark` / `o_state_tint` / `o_state_light`, outline `o_labeled_light o_state_<state>`. Or add the status class to `$o-state-wiring` in `modules/_states.scss` (395 classes, generated, `@extend %o_state_<state>_<style>`, imported last). Never set a colour on a status class in a module.
- Status colour without a label (icon, marker, bar, chart): `o-state-color($state, $role)`, roles `text` (text, icons), `bg` / `soft-bg` (fills), `border` (borders, markers, chart lines), `fg` / `soft-fg` / `soft-border`. Not `$brand-success|danger|warning|info` or `$state-*-text`.
- Fixed colour without a meaning (stars, pen colours): `o-palette($hue, $step)`. Swatch role of a hue: `o-swatch-color($hue, $role)`.
- No new Sass colour variable, no `darken()`/`lighten()`/`rgba($var)` on palette or state colours.
- Token layers (`modules/_tokens.scss`, OO-9994, OO-10043, not in `email.css`): **base** = palette (literal colours: `--o-{hue}-{step}`, `--o-theme{n}-{step}`, the neutral scale `--o-neutral-{step}`, `--o-white`, base colours `--o-base-*` from `$text-color`, `$brand-primary`, `$link-color`, ...; in light each reads its scale step, `var(--o-neutral-750)`), the 22 semantic tokens `--o-text`, `--o-text-muted`, `--o-text-disabled`, `--o-heading`, `--o-bg`, `--o-bg-subtle`, `--o-bg-hover`, `--o-bg-selected`, `--o-bg-raised`, `--o-border`, `--o-border-subtle`, `--o-border-strong`, `--o-primary`, `--o-primary-fg`, `--o-primary-hover`, `--o-primary-text`, `--o-link`, `--o-link-hover`, `--o-focus`, `--o-shadow-color`, `--o-backdrop`, `--o-scrim` (the last 3 are opaque: the rule sets the transparency with `color-mix(in srgb, var(--o-backdrop) 50%, transparent)`; `shadow-color` = all shadows, `backdrop` = dark layer behind a modal dialog, `scrim` = light veil over content, dark in a dark mode), the 56 state tokens `--o-state-{state}-{role}`, and the global elements (buttons, content text and headings: `$o-token-layer-base`, 56); **framework** = layout and generic UI of `org.olat.core.gui` and `org.olat.core.commons.services` (navbar, footer, login, dialogs, tree, toolbar, scope toggle, table, wizard, form elements, tags, message boxes, labels, date picker, ...: `$o-token-layer-framework`, 373); **component** = elements of one feature module (course, course site, QTI tests and question pool, practice, forum, chat, lectures, topic broker, folder, selectus, immunity proof, evaluation form, rating, ...: `$o-token-layer-component`, 437).
- Element token = a token of the three layer maps, 866 in total, `--o-{element}-{part}`. Default `($sass-default, (tokens))` (698: 565 a Sass variable, 68 a Sass expression, 65 a fixed scale step such as `o-palette("yellow", 400)` or `o-neutral(150)`): the Sass value of the theme config feeds the token (client themes keep setting it), the token reads the first listed token whose default has the same colour (follows its override), else the scale step (palette, brand ramp, neutral scale, white), else `--o-base-{name}`. The default can be a Sass expression for a text colour that `o-a11y-color()` adjusts for the background of one rule, e.g. `"link-subtle": (o-a11y-color($link-color, $panel-default-heading-bg), ("link",))`; the breadcrumb, table, course element and forum link tokens reference it. No module calls `o-a11y-color()` (test `rulesReadAdjustedTextTokens`): a new adjusted text colour is a new token. Default `"token-name"` (168): reference to another token of any layer, e.g. `"selectus-review-glow": "primary"` emits `var(--o-primary)`, `"qti-menu-link": "tree-link"`; no Sass variable, set with `$o-tokens`; loop or unknown name stops the compile. Three scales: every default reads the palette (12 chromatic hues, `o-palette("orange", 500)`), the neutral scale with white (`o-neutral(150)`) or the brand ramp (only the brand colour itself and the defaults that derive from `$brand-primary`, the primary or the link tokens; a fixed blue reads `blue`); a colour maths default keeps its source and reads the nearest step of its result (`o-scale-snap($source, darken($source, 5%))`, a client colour keeps the computed result), a text on a fill that needs a ratio `o-scale-on-color($color, $bg, $ratio)` (`_functions.scss`). In light no token holds a literal colour (test `tokenDefaultsReadScales`; `_tokens.scss` has no hex value outside comments and the white backgrounds of the pairs); a text adjusted for its background reads the nearest step with the ratio (`o-scale-a11y-color()`: `toggle-text` neutral-600, `login-help-link` and `badge-row-expanded-link-hover` theme1-600, they derive from `$link-color`). Literal values remain only for the own colours of a client theme. Every token is a `var()` reference. A module reads the element token of its element (`var(--o-selectus-review-glow)`, not `var(--o-primary)`), else an exact token; `_mixins.scss` stays Sass (email).
- Shade token = the darker or lighter colour of an element, semantic or state token, computed at compile time (`$o-token-shades` in `modules/_tokens.scss`, 150 tokens): `"name": ("token", percent)` darkens (114), `("token", percent, "lighten")` lightens (27), `("token", angle, "hue")` turns the hue with `adjust-hue()` (1), `("token", percent, "state")` darkens a state fill or lightens it when it cannot get darker (8, the `-bg-hover|active` of the light buttons and the table filters; `o-contrast-shade()`: a black active filter gets `#1A1A1A` and `#2B2B2B`). When the colour of its token is a scale step (light defaults; not the brand ramp of a theme with an own `$brand-primary`), the shade reads the nearest step of the scale of its token (same palette hue, neutral scale or brand ramp; never another hue) that differs from the token, lies on the side of the maths and keeps the contrast pairs of the shade (`o-token-shade-scale()`), else, for a bright fill at step 400 of a hue of `$o-palette-bright` with dark text, the state goes lighter inside the hue: hover and pressed fill step 300 (`o-token-shade-lighter()`; light: `btn-dirty`, `coursesite-book`, `tag-selected`, `state-warning`, `selectus-rating-b` on yellow-400, `state-success` on green-400; their border shades stay darker), else the computed literal (only for a client colour). Hover and pressed fill of one token are two different steps (`o-token-shade-trio()`), except a bright fill that goes lighter. Button states (13 elements, 52 tokens): `--o-{element}-bg-hover` (10%), `-bg-active` (17%; 16% for a bright fill with dark text, `o-token-active-percent()`, so `#301E06` keeps 4.65:1 on the warning fill), `-border-hover` (12%), `-border-focus` (25%) for `btn-primary`, `btn-default`, `btn-danger`, `btn-dirty`, `btn-primary-light`, `btn-danger-light`, `state-neutral`, `state-success`, `state-warning`, `table-filter`, `table-filter-active`, `coursesite-start`, `coursesite-book`. Hover and pressed states keep the 4.5:1 of the normal state: the `-bg-hover` and `-bg-active` of `btn-primary-light`, `btn-danger-light`, `table-filter`, `table-filter-active` take `o-contrast-shade-amount($fg, $bg, $max)` (`_functions.scss`), the largest amount up to 10% or 17% (steps of 1%) at which the text keeps 4.5:1; `$max` when the text passes at `$max` or already fails on `$bg`; `$max` too when no amount from 3% passes (`$min`): the state keeps 10% or 17% and the text token of the state `{element}-fg-hover`, `-fg-active` (`o-contrast-shade-text()`, `_functions.scss`; follows `-fg` in light) holds the text adjusted for the fill, white or black when `o-a11y-color()` cannot reach 4.5:1 (light: the light buttons hover `neutral-25`, pressed `neutral-50`, the pressed table filter `neutral-250`). The compile stops when one of these 8 fills has the colour of its normal fill (`$o-token-state-fills`). The other 98 keep the percentage of the colour maths they replace (`rating-star-edge`: 20% darker than `rating-star`): tags, context help, immunity proof, `focus-edge`, tables in a message box (`box-*-table-border|stripe-bg|header-bg`), high score podium (`-stop-1|2|4`), labels without status (`labeled-*`), selectus rating buttons, catalog header (`catalog-header-noimage-stop-1|3|4`), state shades for the Bootstrap mixins (`state-*-soft-bg-hover` 5%, `state-*-text-hover` 10%, `state-danger-bg-hover`), ... Suffixes: `-hover`, `-active`, `-focus` (state), `-edge` (darker edge: border, outline, text stroke, e.g. `rating-star-edge`), `-tint` (lighter surface), `-stop-{n}` (gradient stop); a shade for an element without an own token takes the element and role name. It follows its token (Sass variable or `$o-tokens`), `$o-tokens` overrides it like an element token; a run time redefinition (dark mode) redefines the shade tokens too. A mixin with a token argument builds the shade name: `button-variant`, 6 mixins of `_state_variant.scss`, `o-make-glossy-bg`, `labeled-variant`. No `darken()` or `lighten()` of a token colour in a module: add or read a shade token.
- Translucent colour of a token = no token: `color-mix(in srgb, var(--o-backdrop) 50%, transparent)` for `rgba($modal-backdrop-bg, 0.5)` (same alpha). Black shadows read `color-mix(in srgb, var(--o-shadow-color) 20%, transparent)`, the dark modal layer `--o-backdrop`, light veils `--o-scrim`, each with the alpha of the old `rgba()`; the shadows with `rgba(16, 24, 40, a)` read `shadow-color` with the same alpha too. Colours without a role: dark tints read `backdrop` (skeleton, print, quiz overlay, AI feedback, admin tag stripes, `$dropdown-border`, `$o-lp-bg`), the immunity proof shadows `shadow-color`, the navbar highlight line `navbar-highlight` (`var(--o-white)`, not `scrim`: it stays light in a dark mode), the styled peekview `course-style-peekview-bg` (default `$o-cn-style-peekview-bg`, translucent), the stops of `$o-not-available-bg` read `primary`, `not-available-dark`, `not-available-light`. The dark layer of the video comment panel (`_video.scss`) reads `backdrop` 50%. A named `$o-*` variable with a translucent default stays the customisation point, its default is the `color-mix()` (`$o-login-bg-color`); it feeds an element token with that default (`"login-bg": ($o-login-bg-color, ())`; also `brand-box-bg`, `course-style-cover-text-bg`, `lp-bg`, `catalog-header-box-bg`, ...), the token has no contrast pair and no shade token. The state label hovers of `_states.scss` keep `color-mix(in srgb, var(--o-sw-bg), #000 10%)`. Muted text: `var(--o-text-muted)`, disabled text `var(--o-text-disabled)`, never `lighten($text-color, ...)`.
- Bootstrap colour variables that a module reads are framework tokens with the exact value (OO-10043): `input-bg`, `input-fg`, `input-disabled-bg`, `input-placeholder`, `table-border`, `table-striped-bg`, `table-hover-bg`, `dropdown-link`, `dropdown-link-hover`, `dropdown-link-hover-bg`, `dropdown-divider`, `popover-bg`, `popover-border`, `modal-content-border`, `modal-header-border`, `code-block-bg|fg|border` (`$pre-*`), `legend`, `legend-border`, `panel-bg`, `progress-bar-fg`, `thumbnail-border`, `blockquote-border`. A module reads `var(--o-input-bg)`, not `$input-bg`; a client theme keeps setting the Bootstrap variable. White: `--o-white` for text on a fill, `--o-bg` for a surface, `--o-bg-raised` for a popover, dialog, lightbox or floating tool bar. A hex grey within 3 of 255 of a token reads the token (`--o-bg-subtle`, a neutral step). - New customization point: add an element token with a reference default to the map of its layer and read it with `var()`; never a new Sass colour variable.
- New code reads `var(--o-*)`: `color: var(--o-text-muted)`, `border-left: 4px solid var(--o-state-success-border)`. No hex, no `$text-color`/`$gray-*`/`$brand-*`, no new Sass colour variable. `ThemeColorRatchetTest` fails when a module gets more old colour references than `theme_color_baseline.properties` (0 in 0 modules; `color-mix(` and the non-colour variables `-gradient-to`, `-gradient-steps`, `-img`, `-position-left|top`, `-ratio`, `-break`, `-blend-mode` do not count; names with upper-case letters count; `_` in a name counts as `-`). A reference that stays by design has a silent marker: `// o-color-keep(reason)` at the end of a line, `// o-color-keep-start(reason)` ... `// o-color-keep-end` on own lines around a block; reasons `hotspot`, `print`, `brand`, `devtool`, `stored-content`, `gradient`, `mask`, `email`, `mixin-argument`, `vendor-copy`, `a11y-checker`, `client-value` (`KEEP_REASONS`; `client-value`: a value of a client theme that a token cannot carry, `none` or `inherit` next to `transparent` and colours, or a link hover that follows the link colour of the client); the module count excludes it, the baseline line `keep.<reason>` holds the total (105) and must match. Never mark a leftover that a token can replace.
- Client override: `$o-tokens: ("text-muted": "slate-600", "state-success-bg": "green-600", "state-success-fg": "white", "navbar-bg": "primary", "navbar-text": "primary-fg", "navbar-link": "primary-fg", "navbar-tools": "primary-fg", "qti-menu-link": "link", "selectus-review-glow": "orange-500");` in the theme config; key = any semantic, state or element token, value = any token name (`var()` reference, chains allowed, a loop stops the compile), `"{hue}-{step}"`, `"neutral-{step}"`, `"white"` or a colour. ## Colour Palette (user colour choosers)

All user-chosen colours (calendar, course element category, video markers, project avatar, user initials, rooms, page editor blocks, badges, report series) come from one palette in `_palette.scss`: 14 hues (red, orange, yellow, lime, green, teal, cyan, blue, violet, magenta, pink, brown, slate, gray) × 10 text steps (50 to 900) and the fill step 450, plus the theme colours `theme1` … `themeN` (brand colours of the theme, `$o-theme-colors` in `_palette_theme.scss`, default `$brand-primary`). The theme emits every value as `--o-{hue}-{step}` on `:root` in `theme.css` and `content.css`. Step 450 (every hue and theme colour) is the OKLab midpoint of 400 and 500 (`$o-palette-fill-steps`), a fill or shape colour only (white text 2.66:1 to 3.71:1, step 900 text 4.28:1 to 5.99:1): no swatch role, no chooser (`Palette.STEPS` holds the 10 text steps, `Palette.FILL_STEPS` the fill step), the automatic step choices skip it (`o-scale-auto-steps()`); a default reads it by name or with `o-scale-snap(..., $fill: true)` (light: chart bars, `editor-hover-border`, bronze podium, `recorder-record`). The greys are not a hue: the neutral scale `--o-neutral-{step}` (`_palette_neutral.scss`, 18 steps 0, 25, 50, 100, 150, 200, 250, 300, 400, 450, 500, 600, 700, 750, 800, 900, 950, 1000; 0 white, 1000 black; slate-tinted, `$o-neutral-hue` default 260 and `$o-neutral-chroma` default 0.038 change the tint, the lightness stays). Modules never read a step directly, a semantic or element token reads it; the choosers and Java (`Palette.NEUTRAL`) skip it.

- **Swatches:** `$o-swatches` gives each hue the roles `bg`, `fg`, `border`, `soft-bg`, `soft-fg`, `text`, plus tint and dark variants. `o-on-color()` picks the foreground and fails the compile below 4.5:1. The class `.o_swatch_{hue}` sets `--o-sw-*`; components read `var(--o-sw-bg)` etc. Never add a hex literal for a chooser colour.
- **Legacy keys:** stored values (`o_color_lightblue`, `o_cal_blue`, `o_colcat_light_blue`, ...) stay valid through the alias map in `_palette.scss` and `ColorService.resolve()` in Java.
- **Java:** `Theme.init()` reads the `--o-{hue}-{step}` properties from the selected theme's compiled `theme.css` (fallback `light`) into a `Palette`; `ColorService.getPalette()` returns it. No generated palette file exists. A client theme may override the values of `$o-palette` (keep the 14 hue names) and Java follows. `Palette.getThemeColors()` / `ColorService.getThemeColors()` return only the theme colours the theme defines; a stored `theme{n}` above that count resolves to `theme1`.
- Live reference with contrast values: `doc/component-library/colors.html`.

## AJAX Rendering

Components render with `id="o_c{dispatchID}"`. On user action, server re-renders dirty components, responds with JSON `[{action:"updcmp", id:"o_c12345", content:"<html>"}]`, jQuery replaces DOM. Background polling every 5s (with decay) picks up cross-session updates. Form events send `{name, value}` pairs (`o_ffXHREvent`), so checkbox groups keep all values.

Collapsible sections need no per-instance script: one delegated handler in `functions.js` on `.o_section_toggle`.

## Accessibility

- Full chapter: `doc/openolat-frontend.md` 36 (focus management, ARIA patterns, live regions, keyboard patterns, JS helpers, theme rules, known gaps)
- `o-a11y-color($color, $bg)` auto-adjusts for WCAG 4.5:1 contrast
- Focus ring (OO-10043): every control shows `outline: 2px solid var(--o-focus); outline-offset: 2px` on `:focus-visible`; no own focus style in new code, inset ring (`o-focus-ring-inset`) for a control that touches its neighbours or sits in an `overflow: hidden` container. Details in the colour section above and in `doc/openolat-frontend.md` 36.6
- Used extensively in `_config.scss` for button text, toolbar links, etc.
- Bootstrap 3 ARIA attributes on tabs, modals, forms
- `$r.screenreaderOnly("text")` → `<span class="sr-only">` in templates
- Focus after a redraw: one rule in `o_ainvoke()` (since OO-9603). Command 2 records the focused element, the end of the response puts it back when the focus is on `body`. Order: command 11 (first error field only with `validation: true`, else `formItemId`, weak: error field, `[autofocus]`), dialog return, dialog open focus, redraw rule. Nothing happens while an open `<dialog>` has the focus
- Fallback chain (`o_resolveFocusTarget()`): same id, table row key + slot, table, closest surviving ancestor (temporary `tabindex="-1"`), never `body`
- No new focus opt-in classes or `onfocus` hooks (`o_can_have_focus` and `o_info.lastFormFocusEl` are removed); a focusable element needs a DOM id that stays the same across redraws
- Live regions: use `role="status"` / `aria-live="polite"` for async state (AI overlays, `#o_dashboard_edit_live`); `#o_messages` info boxes are NOT announced
- Keyboard: `triggerClick(event, enter, space)` on link buttons; Escape closes the top layer via `o_doEscapeDispatch()`
- Callout triggers: `Link/FormLink.setAriaDialogOpener()` → `role="button" aria-haspopup="dialog" aria-expanded`; `CloseableCalloutWindowController` toggles `aria-expanded` and returns the focus to the trigger (`pushdialogfocus`/`popdialogfocus`). Pass the trigger component, not its DOM id. **New in 21.1.0:** used on action columns, table tools and filters; the focus goes to the first visible element of the callout.
- Disabled links: `LinkRenderer` writes `role`, `aria-disabled="true"` and `aria-haspopup` only for links with an ARIA role (all `Link.BUTTON*` presentations, `setAriaRole`, `setAriaDialogOpener`); plain links and breadcrumbs get no `aria-disabled`. Never `aria-expanded` on a disabled trigger. Do not add `aria-disabled` by hand. The tooltip is `setTextReasonForDisabling(...)`, fallback the translated title.
- Toolbar (`ToolBarRenderer`): the slot lists are in the DOM in visual order (left, center, right, rightEdge), so the tab order is the visual order. `.container-fluid` is the flex container, the center list takes the free space (`flex: 1 1 0`) and wraps its tools inside, right/rightEdge get `margin-left: auto`. Never position slots with floats, CSS `order` or a positive `tabindex` (WCAG 2.4.3, F44).
- Breadcrumb (`BreadcrumbBarRenderer`): `<nav aria-label>` > `<ol>` > plain `<li>`; the current crumb is `<span aria-current="page">`, not a link. `role="menuitem"` only inside the "more" menu (`ul role="menu"`).
